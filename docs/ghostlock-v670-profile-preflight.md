# GhostLock V670 profile preflight

Date: 2026-11-22
Target: TCL 65C9K / T653T01 / MT5896, V8-T653T01-LF1V670 (AU04)

## Profile candidate

The official GhostLock extractor was run on the local stock `boot.img` and `vendor_boot.img`. It recovered the exact kernel release `5.15.192-android14-11`, 166,475 kallsyms, and reported `remove_waiter` unpatched. The raw extractor output is retained at `private/c9k-stock-v670/ghostlock-candidate.conf`.

The cross-checked HOCON candidate is `private/c9k-stock-v670/ghostlock-t653t01-v670-crosschecked.conf`. It has no unresolved `null` fields and satisfies the documented multicast route field bounds.

## Source port status

An analysis-only V670 profile is registered in the local GhostLock source copy at `private/c9k-stock-v670/ghostlock-v670-port/src/devices/tcl_v670/offsets.h`. It contains the exact release, live-measured physical RAM base, firmware-derived `kernel_phys_load` candidate, extracted V670 kallsyms, exact BTF fields recovered from the stock kernel image, derived linear-map candidates, and stock ELF SLUB boot defaults. Static compat MCAST stack-copy geometry has now been reconstructed, but live carrier execution and reclaim remain explicitly unproven. The general route dispatcher refuses every `analysis_only` profile before selecting a carrier.

The V670 split-ABI work now includes a fixed-width helper message protocol and a self-test-only AArch32 helper target. The helper source validates protocol and byte layout only; it has no futex or MCAST live mode and is not connected to an arming route. The profile remains fail-closed.

A source audit found that a direct call to `prepare_kernel_page()` could otherwise let the V670 unproven reclaim enum fall through to Sabrina's reference allocator sequence. An explicit V670 refusal now closes that fallback even if a future caller bypasses the normal `analysis_only` gate. The standalone V670 perf probe now takes its exact x0-site and slide-heuristic definitions from `src/devices/tcl_v670/io_uring_perf_witness.h`; it remains non-arming and is not wired into GhostLock's V643 in-process witness. The current-boot slide-zero result does not establish which perf IP anchor is correct after a nonzero KASLR slide.

The in-process KernelSnitch result is not yet a target witness. The exact V670 ELF resolves the futex hash table to 1024 buckets: `futex_init` counts the four possible CPUs, computes 256 entries per CPU, and passes 1024 as both bounds to `alloc_large_system_hash`. The V670 profile now carries that exact size, and the scanner code counts matches across the configured range and rejects zero or multiple candidates. This uniqueness check has not been run in the V670 path; even one match is not independently tied to the target `mm_struct` or to the perf-sampled page. Live zoneinfo now confirms the 3-GiB physical RAM extent; the 39-bit linear-map VA base is derived from the exact kernel config/ELF.

A separate ARM32 profile inspector was built from `tools/tcl_v670_profile_info.c`; it does not link GhostLock's exploit implementation. It was pushed to the TV, ran using the live `uname`, and reported the V670 profile present with `analysis_only=1`, unproven carrier/reclaim routes, and `primitive_arming=REFUSED`. The temporary inspector was removed afterward. No exploit binary was built or run on the TV.

This completes profile registration, read-only target validation, and static compat MCAST geometry reconstruction. It does not complete an armed GhostLock port: live carrier execution, live physical-load confirmation, unique capture witness, full reclaim behavior, and compatible root handoff remain unvalidated.

## Additional V670 values found (2026-11-22)

- The embedded FDT in local `mboot.img` places `/mmap_info/MI_KERNEL_POOL1/reg` and `MI_KERNEL1_RANGE0/reg` at physical `0x26000000`; the V670 kernel Image header has `text_offset=0`. This gives a firmware-derived `kernel_phys_load=0x26000000` candidate, matching the V643 profile's measured address. A fresh read-only check confirms V670 `/proc/iomem` remains permission-denied, so this is not live-confirmed.
- The live TV reports `/proc/slabinfo` row `mm_struct ... 1024 16 4`: 1024-byte objects, 16 objects per slab, 4 pages per slab (order 2). `/sys/devices/system/cpu/{possible,present,online}` all report `0-3`. The exact kernel config is readable at `/proc/config.gz`: `CONFIG_ARM64_VA_BITS=39`, `CONFIG_NR_CPUS=32`, `CONFIG_SLUB=y`, `CONFIG_SLUB_CPU_PARTIAL=y`, `CONFIG_SLUB_DEBUG=y`, `# CONFIG_SLUB_DEBUG_ON is not set`, and `# CONFIG_KASAN is not set`.
- The V670 BTF blob was recovered directly from the raw stock `v670-kernel.Image` at file offset `0x1ca112c` by `private/c9k-stock-v670/tools/extract_v670_btf.py`. Its length is 5,130,479 bytes and SHA-256 is `592fc45473082728931c2af81ae097904e89425fda17dab791d12118f34fcc40`; that length exactly matches the live `/sys/kernel/btf/vmlinux` file, whose contents SELinux prevents the shell from reading. The embedded BTF confirms `sizeof(mm_struct)=976`, `sizeof(task_struct)=4736`, `sizeof(cred)=176`, `sizeof(rt_mutex_waiter)=88`, `sizeof(struct page)=64`, and `kmem_cache` field offsets including `min_partial=0x10`, `size=0x18`, `cpu_partial=0x2c`. It also confirms the task, credential, and waiter offsets already recorded in the V670 profile. `mm_struct`'s 976-byte C struct and the live 1024-byte SLUB object size are distinct measurements.
- Exact GhostLock-relevant BTF offsets: `task_struct.prio=0x7c`, `normal_prio=0x84`, `pi_lock=0x8e4`, `pi_waiters=0x8f8`, `pi_top_task=0x908`, `pi_blocked_on=0x910`, `cred=0x7f8`, `real_cred=0x7f0`, `seccomp=0x8c0`, `pid=0x638`, `tgid=0x63c`, `atomic_flags=0x5f8`, and `mm_struct.owner=0x348`; `rt_mutex_waiter` has `pi_tree_entry=0x18`, `task=0x30`, `lock=0x38`, `wake_state=0x40`, `ww_ctx=0x50`; `struct page` has `compound_head=0x08`, `slab_cache=0x18`, and `page_type=0x30`. `cred` has `usage=0`, capability sets at `0x28`–`0x48`, and reference pointers `user/user_ns/ucounts/group_info` at `0x80/0x88/0x90/0x98`. The BTF also recovers the supporting security, user, ucounts, group, namespace, ID-map, and file_operations layouts; those exact offsets are now filled in the guarded V670 source profile.
- The reconstructed V670 ELF additionally confirms `init_user_ns`, `init_uts_ns`, `kptr_restrict`, `kmalloc_caches`, `anon_pipe_buf_ops`, `ashmem_misc_fops`, `system_unbound_wq`, and `call_usermodehelper_exec_work`. For indirect fake-`file_operations` callbacks, the profile now uses V670 CFI jump-table entries: ashmem ioctl/compat ioctl/mmap/open/release/show_fdinfo at `0x1465f30/0x1465f34/0x145b6f0/0x145bdb8/0x145bdbc/0x145bf24`, configfs read/bin-write at `0x145b47c/0x145b488`, and noop_llseek at `0x145987c`. The ordinary implementation symbols are different addresses and would fail the CFI callback path. V670 `ashmem_fops.splice_read` is null and there is no matching `copy_splice_read` CFI target, so the profile leaves that callback null. These static values do not validate a route or handoff.
- Exact V670 ELF disassembly reconstructs the compat MCAST stack copy. `compat_sys_call_table[294]` and `sys_call_table[208]` both point to `__arm64_sys_setsockopt.cfi_jt` (`_text+0x145e464`); its `ip_setsockopt` TIF_32BIT path copies a 0x104-byte `group_source_req` at local `sp+0x120`. The setsockopt call-chain frames are 0x10 + 0x80 + 0x40 + 0x10 + 0x290 = 0x370, so the compat copy begins at syscall-entry SP-0x250. In the futex path, `__arm64_sys_futex` uses a 0xa0 frame and `do_futex` passes its local waiter at entry SP-0x130, placing the `rt_mutex_waiter` at futex syscall-entry SP-0x1d0. The overlap is therefore +0x80 from the MCAST copy start; BTF confirms the 0x58-byte waiter fits in the 0x104-byte copy. The profile keeps the route unproven because this is static layout evidence only; the carrier has not been executed on the TV.
- Live `/proc/zoneinfo` reports DMA32 start PFN 131072 with 335872 spanned/present pages, followed contiguously by Movable start PFN 466944 with 450560 spanned/present pages. The combined physical extent is PFN `0x20000..0xe0000`, or `0x20000000..0xe0000000` (3 GiB). With the exact 39-bit V670 linear-map layout, this confirms the profile's 3-GiB direct-map extent `0xffffff8000000000..0xffffff80c0000000`; the virtual base comes from config/ELF, not a live pointer read. `vmemmap_start=0xfffffffe00000000` follows the 64-byte `struct page` layout.
- A fresh read-only memory check reports `MemTotal=2,479,848 kB`; sysfs lists blocks `memory4` through `memory27`, but SELinux denies reading `block_size_bytes`, each block's `phys_index`/`state`, and `/proc/iomem`. These denials prevent an independent sysfs/iomem cross-check; zoneinfo supplies the physical extent above.
- Exact V670 ELF disassembly resolves the stock boot-time SLUB defaults. `mm_cache_init` at `_text+0x1a26c0` calls `kmem_cache_create_usercopy` with a requested object size of `0x3d8` (984 bytes), flags `0x04042000`, and the recorded usercopy range. The live cache stride is 1024 bytes. In `__kmem_cache_create` at `_text+0x45918c`, the code stores `min_partial=5` at BTF offset `kmem_cache+0x10` for that size, and stores `cpu_partial=6` at `kmem_cache+0x2c` when CPU partials are enabled and the cache is not debug-enabled. The V670 config enables `CONFIG_SLUB_CPU_PARTIAL`, disables `CONFIG_SLUB_DEBUG_ON`, and excludes KASAN. The vendor_boot v4 bootconfig is exactly 104 bytes and contains only `androidboot.boot_devices=1c660000.mtk-mmc-fcie`, `androidboot.console=ttyS0`, and `androidboot.fstab_suffix=merak`; the live cmdline has no `slub_debug=`/`slab_debug=` parameter. The matching Android debug-symbol module's `ads_slub_debug` is diagnostic state reflecting `__slub_debug_enabled()`, not a cache-tuning hook. These independent image/config/bootconfig facts make `(min_partial,cpu_partial)=(5,6)` the strongly supported stock initialization values; the profile now records them as boot defaults. They are not a direct live read: `/proc/bootconfig` and `/sys/kernel/slab/mm_struct/{min_partial,cpu_partial}` are denied to shell, the sysfs nodes are mode `0600`, and a privileged post-boot write cannot be excluded. TCL's exact downstream source remains absent. The profile stays analysis-only.
- Exact V670 ELF disassembly also resolves the futex hash-table size. Live possible CPUs are `0-3`; `futex_init` computes `256 * nr_possible_cpus`, rounds to a power of two, and passes that result as both the lower and upper bounds to `alloc_large_system_hash`. Its clamp fixes the table at 1024 buckets. The V670 profile and scanner now use that exact size, count candidate matches, and refuse zero or multiple matches. This code has not been run in a V670 carrier path, and a unique match still needs an independent tie to the target `mm_struct` and captured page. No scanner result has been promoted to a target witness.
- TCL's public [kernel-source index](https://github.com/TCLOpenSource/TCL_Kernel_OpenSource/blob/main/README.md) has no matching T653T01 / G08 / MT5896 V670 / 5.15.192 entry. Its [mt9653 source tree](https://github.com/TCLOpenSource/mt9653) does include [`mt5896_defconfig`](https://github.com/TCLOpenSource/mt9653/blob/main/arch/arm64/configs/mt5896_defconfig), confirming it is useful for the same SoC family; the index identifies it as Android R / 5.4.190. The nearby MT9618 Android U 5.15.180 and MT9653FTV Android U 5.15.167 trees are also not exact matches. AOSP `android14-5.15-2025-10_r3` is a plausible baseline by date, not proof of TCL's base revision and not a substitute for vendor patches.
- The current extractor identifies `multicast_waiter` only as a medium-confidence route suggestion (candidate waiter offset 96, buffer size 264) and cannot derive `pselect_waiter_shift` because `futex_wait_requeue_pi` is absent from its recovered kallsyms set. Those candidates are not runtime validation. The unique page-capture witness remains outstanding.
- A read-only pagemap probe reported `PRESENT=1`, `SWAPPED=0`, but `PFN_NONZERO=0`: the shell can read its pagemap entry while PFN bits are masked. The separate perf feasibility probe proves sampling works, but does not identify a unique reclaim witness.

## Non-arming perf feasibility probe

Built the reference project's explicitly non-arming `tcl_v643_uring_perf_probe.c` with Android NDK 27.3.13750724, then ran it on V670 with one io_uring ring and 5,000 loops. It reported 1,872 own perf samples for both `ring_mmap` and `sqe_mmap`, with zero lost samples. In the SQE run, a 16-KiB-normalized register candidate had 15 votes and its top associated sample IP was `io_uring_mmap+0xc8` in the V670 ELF (3 IP votes); this lies in the static interval where `x0` is expected to hold the selected page pointer. The probe groups all registers and does not verify `x0`, a unique target page, or reclaim reuse, so this is only signature feasibility. The temporary binary was removed from `/data/local/tmp`. After the run, AVB remained green, vbmeta locked, SELinux enforcing, and `perf_event_paranoid=-1`.

Built a separate V670-only signature probe that records only ARM64 `x0` at `io_uring_mmap+0xc8` and accepts an explicit KASLR slide. The TV's 32-bit process produces `PERF_SAMPLE_REGS_ABI_32`; on the AArch64 perf path this labels a compat task, while the kernel-mode register sample still supplies the AArch64 `pt_regs` sequence, with index 0 equal to `x0`. On the current boot, the runtime IP matched the link-time address (slide 0); `/proc/config.gz` reports `CONFIG_RANDOMIZE_BASE=y`, so the expected IP must be recalculated after reboot. With one ring and 20,000 loops, it collected 12,449 ring-mmap and 12,370 SQE-mmap samples, zero lost; exact-site hits were 3 and 9 respectively. Every hit in each mode yielded one stable, distinct 16-KiB-normalized direct-map `x0` candidate. This confirms the V670 instruction/register signature and distinguishes ring from SQE mappings for this boot. It still does not associate either pointer with the target `mm_struct` slab page or prove reclaim reuse. The temporary binary was removed from `/data/local/tmp`.

Added an `auto` mode to that standalone probe to retain every x0 candidate whose sampled IP has the known site offset modulo a 2-MiB alignment. The mode labels results heuristic and prints every candidate rather than selecting one. A fresh one-ring, 20,000-loop run collected 12,835 ring-mmap and 13,354 SQE-mmap samples, zero lost. It found the same IP `0xffffffc0088c9cac` in both modes, with 7 ring hits and 11 SQE hits; both imply slide 0 under the 2-MiB alignment assumption, and the normalized x0 pointers differ by mapping kind. This is consistent with the exact V670 `io_uring_mmap+0xc8` site on the current boot, but the residue match and ring/SQE agreement are still heuristic, and this does not provide a known target KVA or a reclaim witness. The probe binary was removed from both the TV and local source directory after the run.

## Resume audit (2026-11-22)

The local BTF artifact was rechecked: length 5,130,479 bytes and SHA-256 `592fc45473082728931c2af81ae097904e89425fda17dab791d12118f34fcc40` match the recorded extraction. This verifies artifact consistency, not runtime equivalence.

The source profile remains `analysis_only=1`. Source inspection finds refusal paths in `src/core/main.c`, `src/core/fops.c`, and the V670-specific reclaim barrier in `src/core/util.c`. No executable was built or run during this audit, and no TV state was changed.

Two provenance limitations matter when resuming:

- `ghostlock-t653t01-v670-crosschecked.conf` is an earlier extractor candidate. Its comment still says V670 BTF is unavailable, whereas embedded stock-image BTF was subsequently recovered. Its route suggestion must not be treated as equivalent to the later guarded source profile or as runtime validation.
- `tests/profile_guard.c` targets V643 (`5.15.180-android14-11`), not V670. Its results cannot establish V670 guard coverage. The standalone profile inspector is also only a metadata inspection, not proof of exploit behavior.

Remaining unvalidated items are unchanged: live physical kernel load, carrier behavior, an independent target-page witness, runtime allocator settings/reclaim behavior, and root handoff. The analysis-only status remains appropriate.
